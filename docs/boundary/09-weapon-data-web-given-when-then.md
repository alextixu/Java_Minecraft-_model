# 邊界行為：Given / When / Then（R2b 資料驅動武器＋R6 網頁後台）

> 狀態：**已確認（最終版）**。決定在 [10](10-weapon-data-web-open-questions.md)：先回「全部照建議」，之後改為「照審查建議版」，Q7 再調整。每一列都會變成一個測試，測試的說明文字照抄這裡的三行。第一版的本檔在 git 歷史（commit `18c4487`）。
> 流程：boundary-first 第 3 步。

## 數字的前提

- 4 件預設裝備的數值和現在完全相同（R2 的 O7、N3）：

| id | 欄位 | 外觀 | 修飾 |
|---|---|---|---|
| `heavy_sword` | 主手 | 原版獄髓劍 | 攻擊力 +6、移動速度 −30%、攻擊速度 −40% |
| `dagger` | 主手 | 原版鐵劍 | 攻擊力 +2、暴擊率 +0.25、移動速度 +10% |
| `evasion_chestplate` | 胸甲 | 原版鎖鏈胸甲 | 迴避率 +0.15 |
| `heavy_armor` | 胸甲 | 原版鐵胸甲 | 護甲 +8、移動速度 −15% |

- 測試用的自訂武器 `halberd`（戟）：主手、外觀用內建貼圖 `halberd_netherite`（hanhanpx，32×32，放在 jar 裡）、攻擊力 +9、移動速度 −20%。
- 玩家空手：攻擊力 1.0、移動速度 0.1。

## 成功條件（一把資料驅動的武器正常運作，要同時成立的事）

1. 設定檔合法：JSON 語法正確、格式版本認得；檔名是合法 id；欄位是已知的；只引用已註冊的數值、每個數值最多一筆；數字有限、百分比大於 −100%；外觀指向存在的原版物品，或存在而且合法的 PNG。
2. 啟動時，每個合法的檔案都變成一個物品，有名稱和外觀。第一次啟動時，設定資料夾自動建立，內含 4 件預設武器。
3. 拿著或穿著時，修飾照 R2 的規則生效（T1 不變）。
4. 客戶端照外觀畫出物品；tooltip 顯示名稱和修飾。
5. 執行中改了定義（指令或網頁），所有同種武器都換成新定義，手上正拿著的立刻重算。
6. 網頁列得出所有武器和目前的數值，改得了數值、名稱、外觀，存回設定檔。
7. 網頁只接受允許的來源。
8. 遊戲內測試不受使用者改過的設定影響。

H 系列是全部條件成立的情況，B 系列是逐一破壞上面的條件推導出來的。

## H：正常情況

| # | Given | When | Then | 對應 |
|---|---|---|---|---|
| H1 | 全新的遊戲資料夾，沒有 `config/mobarmory/` | 啟動遊戲、進世界 | 自動建立 `config/mobarmory/weapons/`，內含 4 個 JSON；4 件裝備的數值和現在一樣；主手重劍時速度 0.1 → 0.07，放下回 0.1 | R2b、T1 |

| H10 | 使用者已經在網頁把重劍改成 +16 | 執行 `gradlew runGameTestServer` | 遊戲內測試全過，用的是預設的 +6（測試在獨立資料夾、從內建預設開始） | 測試隔離 |

## 還沒列進來的（之後的階段才處理）

- 怪物的 API（R4 恢復後）：照 `WeaponAdmin` 的形狀加 `MobAdmin`，路徑 `/api/v1/mobs` 已預留。
- 物品清單不同時自動同步（B19）：要在連線時把武器檔傳給客戶端並重開，這次不做。
- 網頁上傳新貼圖：這次不做（Q5 B），新貼圖要放進 jar 再 build。
- 網頁刪除武器：這次不做，刪除會讓世界裡的武器消失，要另外設計確認流程。
- 盔甲穿在身上的自訂貼圖：這次只能選原版材質。
