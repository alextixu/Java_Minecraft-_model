## 第一輪：設計

### Q1 SOLID 判斷

- **徵兆**：玩家要加數值，但數值寫在 Java 的 `content/ModStats`。每加一個數值都要改程式、重新 build，違反 O。
- **處方**：把「遊戲裡有哪些數值」搬到 `config/mobarmory/stats/`。`ModStats` 剩下 Java 程式要引用的 7 個內建數值，也是預設檔的內容；常數和型別都不變，所以引用它的程式（戰鬥效果、怪物、combo 分支）不用改。

- **A（建議）同意**
- B 不是這個問題：數值留在 Java，玩家只能加武器
- C 這次不要重構，只做「讀額外的數值檔」，內建數值不寫成檔案

### Q2 Pattern

- **A（建議）照 R2b 武器**：一個數值一個 JSON，`StatStore` 介面加資料夾、記憶體兩種實作，用 `StatCatalog.builder()` 建登記表，啟動時讀一次。
- B 一個大檔 `stats.json` 放全部的數值：檔案少，但玩家分享一個數值時要複製一段 JSON，而不是一個檔。
- C 直接寫，不抽 `StatStore`：測試就得碰真的資料夾。

- **A（建議）同意**
- B 有要劃掉或補上的檔案

## 第二輪：規則

### Q4 內建的 7 個數值檔可以改嗎

- **A（建議）可以改數字，不能改種類**：預設值、上下限、`floor` 照檔案。但「自訂屬性 ↔ 原版屬性」，以及原版屬性指向哪一個，不能改；改了就啟動失敗。
  - 種類不能改的原因：Java 的戰鬥效果、怪物定義依賴它們的種類。例如暴擊率必須是自訂屬性，攻擊力必須是 Minecraft 的攻擊力。
- B 內建數值完全唯讀：檔案只是說明，改了也沒用。比較安全，但玩家會以為改了有效。
- C 什麼都可以改：可能把暴擊率改成指向 Minecraft 的護甲，戰鬥規則會錯亂。

### Q5 內建數值的檔案被刪掉

- **A（建議）用內建值，log 寫一行警告，不自動寫回**：遊戲能開；不自動寫回，避免蓋掉玩家想留空的資料夾。要還原時刪掉整個 `stats/` 資料夾，就會重新寫出 7 個預設檔。
- B 啟動失敗：和武器一致，但只是刪錯一個檔，遊戲就開不了。
- C 自動寫回預設檔。

### Q6 新數值可以對應原版屬性嗎

- **A（建議）可以**：加上 `"attribute": "minecraft:..."`，效果是 Minecraft 自己的，例如跳躍力、擊退抗性、體型。這是玩家不寫 Java 也能做出「有效果」的數值的唯一方法。
- B 只能新增純數值。

### Q7 新數值在遊戲裡顯示什麼名稱

- **A（建議）選填 `name`**：執行時資源包（已經用來放上傳的貼圖）多提供一個語系檔，tooltip 和 `/mobarmory stats` 顯示這個名稱。只用在自訂屬性；對應原版屬性的數值，顯示 Minecraft 自己的名稱。
- B 不提供：顯示翻譯鍵，例如 `attribute.name.mobarmory.luck`。玩家要另外做一個資源包放名稱。

### Q8 執行中能不能改數值

- **A（建議）不能，要重開遊戲**：
  - 新數值本來就要重開，因為屬性登記表在啟動後就凍結。
  - 既有數值的預設值，在每種生物的屬性建好之後就寫死了，執行中改了也套不到已經存在的生物種類上。
  - 所以 `/mobarmory reload` 和網頁「從檔案重新載入」只重新載入武器。
- B 執行中可以改既有數值的上下限、`floor`，只影響武器的疊加計算，不影響生物的預設值：規則會分成兩半，容易誤會。

### Q9 檔案寫錯

- **A（建議）啟動失敗**：log 寫出檔名和欄位，所有問題一次列出，和 R2b 武器的 O7 一樣。略過寫錯的數值檔，會讓用到它的武器也跟著失敗，不如直接說清楚。
- B 略過寫錯的檔案，log 警告。

### Q10 網頁

- **A（建議）不加新功能**：`GET /api/v1/stats` 本來就列出登記表，所以武器表單會自動出現新數值，顯示它的 id；中文名稱只有內建的 7 個有。
- B 網頁可以新增數值：寫出檔案，標「待重開」，像新增武器一樣。功能比較完整，但不在最小範圍。

### Q11 多人

- **A（建議）每位玩家要有同一組 `stats/*.json`，內容最好也一樣，寫進 README 的多人規則**：屬性登記表不同就連不上（平台限制）。
- B 伺服器同步數值定義給客戶端：做不到，屬性登記表在連線前就要一樣。
